# Gym Studio MVP

Decision: independent NestJS backend with PostgreSQL. The existing gym, equipment, and geometry validators stay in TypeScript and are shared with the server. Go/Fiber in `dashboard-backend` and the NestJS setup in `vk-backend-v2` were inspected; their application-specific modules and secrets were not copied.

1. Studio experience: dashboard, create gym wizard, recent designs, simplified builder, equipment picker, library customization, reusable custom equipment, and gym templates.
2. Account workspace: signup/signin, confirmation/recovery, private cloud saves, explicit guest import, local offline cache, account isolation, revision conflicts, backups.
3. Independent backend: `../gym-studio-backend`, own dependencies/build/Dockerfile, PostgreSQL pool and migrations, local persistent PGlite for a zero-setup trial, Nest account/equipment modules.
4. Equipment photos: camera/gallery inputs, upload preparation, server-side provider analysis, measurement review with provenance, editable geometry templates, save to library, use an independent copy in a gym. No provider key is required for the labelled local demo. A real provider key is required to identify an actual photo; demo responses do not recognize image contents.
5. Operational MVP: server-enforced sessions/CSRF/account ownership, password hashing, expiring one-time recovery tokens, durable request limits and research cache, bounded provider calls, frontend reverse proxy, independent container builds, local Compose rehearsal and deployment instructions.

Local checks performed: frontend production build and independent backend production build passed; the full frontend/model/server suite passed all 1,500 tests, and the independent backend suite passed all 20 tests. Checks include Nest routing, email confirmation, token recovery, equipment auth, frontend sync/design/preset behavior and printable geometry exports. The running proxy/API full flow passed with customized equipment placed in a saved gym, signout/signin, password recovery and database survival after a backend restart. Both deployment containers built, and the real PostgreSQL/Mailpit stack passed signup confirmation, equipment/gym saving, password recovery and restoration after container restarts. The backend dependency audit reported zero vulnerabilities. The browser tool blocked access to the local tab, so browser interaction must not be represented as verified in this run.

Before live launch: provision private PostgreSQL and backups; set the HTTPS site domain, real SMTP, AI provider key, model, and spending limits; deploy both services with the same public origin; verify email delivery, camera capture on HTTPS, and backup restoration on that deployment. Billing, team sharing, and arbitrary photorealistic mesh reconstruction are not part of the requested MVP.

Integration follow-up: the existing backend OpenRouter configuration passed a live product research lookup through the frontend proxy. The resulting bench was customized, saved to the private library, placed in a saved gym and restored after signout/signin, password recovery and a backend restart. Actual equipment photo recognition has not been exercised with a real photo; image request payloads and the local photo demo are covered by automated tests. This follow-up passed 20 backend tests, 43 focused equipment/workspace/model tests and both production builds. Cached equipment results now bypass the atomic quota reservation, the frontend reads STUDIO_BACKEND_URL from its .env, and the local development inbox survives restarts. The placeholder DATABASE_URL in the local backend .env was backed up under ignored .data and cleared to use the persistent embedded database; the existing AI settings were preserved.

Furniture follow-up: a real IKEA MALM bed photo, supplied without product text, passed the configured OpenRouter lookup in an isolated local database. The response identified the bed and used the new template-bed with separate frame, legs, mattress, headboard and optional pillows. A width override, custom library save, room placement and signout/signin restoration passed. Geometry bounds and varied parameter combinations passed along with the AI/model, backend and thumbnail tests (44 checks). Generic block results are explicitly labelled placeholders. Template/prompt changes invalidate old text lookup caches. The default bed thumbnail was rendered offline from the actual Manifold mesh because the browser renderer download timed out. Existing saved block parts are preserved and require a new lookup to become beds; they are not silently converted. Restart the user's backend after exporting these model updates.

Generated-model follow-up: real photos now request the universal component renderer (template-assembly), with a strict schema forcing 3–24 coloured primitives rather than a per-product template. A real photo-only lookup identified the MALM bed and generated six components (headboard, footboard, two side rails, centre support and mattress). Editing, private library saving, room placement and fresh-login restoration passed in the isolated API/database test. Bounded numeric geometry, worker construction, library/document validation, exact overall scaling and unsafe-input rejection have automated tests. The review exposes component shape, colour, size, position and rotation. This initial component reconstruction does not promise photorealism, textures, exact hidden geometry or exact photo scale. Backend dev watch mode was tested with a source modification and successful automatic restart; production start remains un-watched.
